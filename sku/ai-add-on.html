Positioning

Structured-data tooling, not "AI to run the utility."

The studio doesn't sell AI as something to run a utility. It sells curated tooling that lets EA, SA, and BA teams accelerate analysis of their own architecture — when that architecture is already captured in the structured form the building blocks define.

The add-on operates on ArchiMate model data, capability maps, and the canonical data model. It does not analyze free-form documents, summarize incident reports, or generate operational decisions. Customer brings their own AI credentials. The studio never receives the customer's model data.

Two components

What ships in the add-on

B-01 · AI Prompt Library

10–12 versioned, viewpoint-specific prompts with explicit input/output schemas. Each prompt is benchmarked against an internal eval set so regressions are detectable when models change.

  • Capability Gap Analysis (as-is vs. building-block reference)
  • Application Cooperation Review
  • Application Consolidation Candidates
  • Data Quality / Canonical-Model Conformance
  • Integration Pattern Recommendation
  • Compliance Control Mapping Check
  • Maturity Heat-Map Generator
  • Roadmap Sequencing Assistant
  • Architecture Decision Record (ADR) Drafter
  • Stakeholder Brief Generator

B-02 · Python/Archi Connector

Open-source-friendly local tooling that exposes .archimate model data to a prompt-runner. Runs entirely on customer-controlled systems; the studio never sees customer model data.

  • Read .archimate files, extract elements and relationships
  • Project ArchiMate views into the prompt input schema
  • Run prompts against multiple LLM backends
  • Cloud backends: Anthropic Claude, OpenAI
  • Local backend: Ollama (full air-gap option)
  • Output handling — JSON, CSV, ADR Markdown, ArchiMate update files
  • Customer-owned credentials, never transmitted to the studio

Data handling

How customer data flows

This is the section a CISO or security review will read first. The architecture is built around "the studio never receives customer model data" — a property that holds whether the customer chooses a cloud or local LLM backend.

What the studio sees: license activation calls and update-channel pulls. What the studio never sees: customer ArchiMate models, prompt content, prompt outputs, LLM responses. Air-gap option: customers on Ollama have zero outbound LLM traffic — the entire prompt run is local.
Why the AI add-on is licensed separately

So a CISO review of AI never blocks a building-block license.

If the AI capability were bundled into F-01, every C-01 / T-01 customer would have to clear an AI security review before licensing the core architecture. That review can take 6–12 months at a typical utility. Decoupling means the building blocks ship cleanly while the AI layer goes through its own separate review on its own timeline.

Customer benefit

  • License F-01 / C-01 / T-01 without an AI security review.
  • Add the AI layer later — even years later — without re-licensing the building blocks.
  • Trial Ollama (local) before committing to cloud LLM use.
  • Cancel the AI subscription without losing access to the building blocks.

Studio benefit

  • Building-block sales aren't gated by AI risk reviews.
  • The AI layer can be priced as recurring (subscription) without forcing the building block into the same model.
  • AI tooling can change — models replaced, prompts revised — without renegotiating the building-block license.
  • Customers who never want AI can still be the studio's customers.
Build status & open questions

What's still being decided

  • Phase 1 prompt count AI Realist's view: ship 3–4 prompts in Phase 1 with high signal-to-noise and a real eval set, not all 10–12. The connector matters more than the prompts; prompts get replaced, the connector compounds. Current plan: ship Capability Gap, Application Cooperation, Compliance Mapping Check, and Stakeholder Brief in Phase 1.
  • Eval set construction Internal eval set for each prompt — ground-truth examples that detect regression when models change. How many examples per prompt? Currently planning 8–12 per prompt minimum.
  • Local model support depth Ollama is the v1 local backend. Performance varies by prompt — some prompts work well on local 8B-class models, others need 70B+. Document the trade-off explicitly.
  • Output schema stability Prompt outputs need stable schemas if they're going to be ingested by downstream tools. Schema versioning vs. permissive parsing — leaning toward strict versioned schemas.
  • Connector as open source Open the connector for community contribution vs. license-protected like the prompts? Trade-off: openness accelerates adoption vs. dilutes the subscription value.
